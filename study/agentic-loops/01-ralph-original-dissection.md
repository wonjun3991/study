# 01 — Ralph 원본 해부 (Geoffrey Huntley)

> **3줄 요약**:
> 1. **메인 컨텍스트와 서브 컨텍스트를 분리**해서, 메인(Opus)이 사양과 `IMPLEMENTATION_PLAN.md`를 보고 "지금 가장 중요한 한 가지"를 골라잡으면, 서브에이전트 수백 개가 사양/코드 읽기를 병렬로 처리해서 요약을 메인에게 돌려준다.
> 2. 메인이 그 요약을 들고 직접 구현·테스트·커밋·push 까지 한 다음 `IMPLEMENTATION_PLAN.md`에 진척과 새 발견 사항을 적어넣고 차례를 종료한다.
> 3. bash 무한 루프가 그걸 받아 **새 프로세스로 처음부터 다시 시작** — LLM 기억은 0으로 초기화되고 파일과 git만 살아남는다. 이 사이클을 **사람이 Ctrl+C 누르거나 `MAX_ITERATIONS` 카운터가 다 찰 때까지** 반복한다 (LLM 본인은 "끝났다"고 선언할 권한이 없음).

## 0. 5개 파일이 만드는 시스템

저장소에 들어있는 진짜 모든 파일:

| 파일                       | 역할                                                    | 누가 작성하나                  |
| ------------------------ | ----------------------------------------------------- | ------------------------ |
| `loop.sh`                | bash 구동 스크립트(driver). 무한 루프.                          | 사람이 1번 작성, 그 후 안 건드림     |
| `PROMPT_build.md`        | 매 반복(iteration)마다 주입되는 **빌드 모드** 목표 프롬프트(goal prompt) | 사람이 1번 작성                |
| `PROMPT_plan.md`         | 매 반복마다 주입되는 **계획 모드** 목표 프롬프트                         | 사람이 1번 작성                |
| `AGENTS.md`              | 프로젝트 운영 규칙 (빌드/테스트/린트)                                | **LLM(거대 언어 모델)이 직접 갱신** |
| `IMPLEMENTATION_PLAN.md` | 현재 작업 상태/할 일(TODO)                                    | **LLM이 직접 갱신**           |
|                          |                                                       |                          |

5개 중 **3개(`loop.sh`, `PROMPT_*.md`)는 사람이 작성, 2개(`AGENTS.md`, `IMPLEMENTATION_PLAN.md`)는 LLM이 작성**. 사람과 기계의 책임 경계가 파일 단위로 깔끔하게 분리됨.

> **첫 번째 의문**: 왜 `IMPLEMENTATION_PLAN.md`가 저장소에 거의 빈 파일로 있을까?
>
> 실제 파일 내용:
> ```
> <!-- Generated by LLM with content and structure it deems most appropriate -->
> ```
> 한 줄. 이게 전부.
>
> **읽어낸 의도**: "구조까지 LLM이 정해라". 사람은 형식(schema)을 강요하지 않고, LLM이 매 반복에서 가장 유용하다고 판단하는 형식으로 자유롭게 쓰게 함. 이는 **Ralph의 핵심 철학 — "외부 파일이 공유 상태이되, 그 형식조차 학습 결과"** 와 일치.

## 1. `loop.sh` — bash 한 페이지로 끝나는 구동 스크립트

### 1-A. 전체 원본 텍스트

```bash
#!/bin/bash
# Usage: ./loop.sh [plan] [max_iterations]
# Examples:
#   ./loop.sh              # Build mode, unlimited iterations
#   ./loop.sh 20           # Build mode, max 20 iterations
#   ./loop.sh plan         # Plan mode, unlimited iterations
#   ./loop.sh plan 5       # Plan mode, max 5 iterations

# Parse arguments
if [ "$1" = "plan" ]; then
    MODE="plan"
    PROMPT_FILE="PROMPT_plan.md"
    MAX_ITERATIONS=${2:-0}
elif [[ "$1" =~ ^[0-9]+$ ]]; then
    MODE="build"
    PROMPT_FILE="PROMPT_build.md"
    MAX_ITERATIONS=$1
else
    MODE="build"
    PROMPT_FILE="PROMPT_build.md"
    MAX_ITERATIONS=0
fi

ITERATION=0
CURRENT_BRANCH=$(git branch --show-current)

echo "━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━"
echo "Mode:   $MODE"
echo "Prompt: $PROMPT_FILE"
echo "Branch: $CURRENT_BRANCH"
[ $MAX_ITERATIONS -gt 0 ] && echo "Max:    $MAX_ITERATIONS iterations"
echo "━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━"

if [ ! -f "$PROMPT_FILE" ]; then
    echo "Error: $PROMPT_FILE not found"
    exit 1
fi

while true; do
    if [ $MAX_ITERATIONS -gt 0 ] && [ $ITERATION -ge $MAX_ITERATIONS ]; then
        echo "Reached max iterations: $MAX_ITERATIONS"
        break
    fi

    cat "$PROMPT_FILE" | claude -p \
        --dangerously-skip-permissions \
        --output-format=stream-json \
        --model opus \
        --verbose

    git push origin "$CURRENT_BRANCH" || {
        echo "Failed to push. Creating remote branch..."
        git push -u origin "$CURRENT_BRANCH"
    }

    ITERATION=$((ITERATION + 1))
    echo -e "\n\n======================== LOOP $ITERATION ========================\n"
done
```

### 1-B. 줄 단위 해부

#### `cat "$PROMPT_FILE" | claude -p ...` — 진짜 핵심 한 줄

이 한 줄이 Ralph의 정체다. 풀어 쓰면:

| 토막 | 해석 | 왜 이렇게 |
|---|---|---|
| `cat PROMPT.md` | 매 반복 시작에 프롬프트 파일을 **다시 읽음** | 사람이 프롬프트를 수정하면 **다음 반복부터 자동 반영**. 즉 실시간 갱신(hot reload). |
| `\| claude -p` | 표준 입력(stdin)으로 프롬프트 주입, `-p`는 비대화형 모드(headless) | 매 호출마다 **새 프로세스 = 새 컨텍스트 윈도우(fresh context window)**. 이게 `/ralph-loop` 같은 플러그인 류와의 가장 큰 차이. |
| `--dangerously-skip-permissions` | 도구 호출(tool call) 자동 승인 (이른바 YOLO 모드, 무조건 허용) | 야간 무인 실행이 목적이라 사람 개입 zero. |
| `--output-format=stream-json` | 구조화된 로그 | 나중에 grep/분석. 무엇이 잘못됐는지 사후 추적 가능. |
| `--model opus` | 비싸고 똑똑한 모델 사용 | 매 반복 "다음 가장 중요한 일은 뭐?"라는 메타 결정을 LLM이 함. 멍청한 모델이면 무한 같은 일 반복. |

> **핵심 관찰**: 종료 조건을 "LLM이 stop_reason을 반환할 때"가 아니라 **"사람이 Ctrl+C 누를 때"** 또는 **`max_iterations` 도달**로 잡았다. LLM에게 "끝났다"고 선언할 권한 자체를 주지 않는 설계.

#### `git push origin "$CURRENT_BRANCH"` — 매 반복 종료 후 push

각 반복이 끝나면 **무조건 push**. 이건 단순한 백업이 아니라 의도적 설계:

1. **체크포인트(checkpoint)**: 사람이 자다 일어나도 git log에 모든 진척이 남음. 반복 N이 망쳤으면 N-1로 되돌림(reset).
2. **외부 CI(지속 통합) 트리거**: push가 GitHub Actions 같은 CI를 깨움 → 별도 환경에서 빌드/테스트 검증 → 다음 반복이 그 결과를 `IMPLEMENTATION_PLAN.md`에 업데이트.
3. **분산 협업 가능성**: 여러 머신에서 같은 브랜치로 ralph 가능 (이론상). 실전에선 거의 안 쓸 것 같지만 가능성은 열려있음.

> **읽어낸 의도**: Ralph의 "외부 영속 상태"는 단순 파일이 아니라 **git 원격 저장소(remote)**. 파일시스템보다 한 단계 더 멀리, 더 신뢰 가능한 상태 저장소.

#### 인자 파싱 — "build / plan" 두 모드 제공

```bash
if [ "$1" = "plan" ]; then
    PROMPT_FILE="PROMPT_plan.md"
elif [[ "$1" =~ ^[0-9]+$ ]]; then
    PROMPT_FILE="PROMPT_build.md"
```

`./loop.sh` (build) vs `./loop.sh plan` 만 다름. 즉 **동일 구동 스크립트가 입력 프롬프트만 바꿔서 두 가지 다른 인지 모드를 구동**. 이게 §3에서 볼 plan-vs-build 분리와 맞물림.

## 2. `PROMPT_build.md` — 매 반복 주입되는 빌드 목표

### 2-A. 전체 원본 텍스트

```
0a. Study `specs/*` with up to 500 parallel Sonnet subagents to learn the application specifications.
0b. Study @IMPLEMENTATION_PLAN.md.
0c. For reference, the application source code is in `src/*`.

1. Your task is to implement functionality per the specifications using parallel subagents.
   Follow @IMPLEMENTATION_PLAN.md and choose the most important item to address.
   Before making changes, search the codebase (don't assume not implemented) using Sonnet subagents.
   You may use up to 500 parallel Sonnet subagents for searches/reads and only 1 Sonnet subagent
   for build/tests. Use Opus subagents when complex reasoning is needed (debugging, architectural decisions).
2. After implementing functionality or resolving problems, run the tests for that unit of code that was improved.
   If functionality is missing then it's your job to add it as per the application specifications. Ultrathink.
3. When you discover issues, immediately update @IMPLEMENTATION_PLAN.md with your findings using a subagent.
   When resolved, update and remove the item.
4. When the tests pass, update @IMPLEMENTATION_PLAN.md, then `git add -A` then `git commit`
   with a message describing the changes. After the commit, `git push`.

99999. Important: When authoring documentation, capture the why — tests and implementation importance.
999999. Important: Single sources of truth, no migrations/adapters. If tests unrelated to your work fail,
        resolve them as part of the increment.
9999999. As soon as there are no build or test errors create a git tag. If there are no git tags
         start at 0.0.0 and increment patch by 1 for example 0.0.1 if 0.0.0 does not exist.
99999999. You may add extra logging if required to debug issues.
999999999. Keep @IMPLEMENTATION_PLAN.md current with learnings using a subagent — future work depends
           on this to avoid duplicating efforts. Update especially after finishing your turn.
9999999999. When you learn something new about how to run the application, update @AGENTS.md using
            a subagent but keep it brief.
99999999999. For any bugs you notice, resolve them or document them in @IMPLEMENTATION_PLAN.md using
             a subagent even if it is unrelated to the current piece of work.
999999999999. Implement functionality completely. Placeholders and stubs waste efforts and time
              redoing the same work.
9999999999999. When @IMPLEMENTATION_PLAN.md becomes large periodically clean out the items that are
               completed from the file using a subagent.
99999999999999. If you find inconsistencies in the specs/* then use an Opus 4.5 subagent with
                'ultrathink' requested to update the specs.
999999999999999. IMPORTANT: Keep @AGENTS.md operational only — status updates and progress notes
                 belong in `IMPLEMENTATION_PLAN.md`. A bloated AGENTS.md pollutes every future loop's context.
```

### 2-B. 줄 단위 해부

#### `0a/0b/0c` — "행동 전 읽기" 강제

매 반복의 첫 행동이 **읽기 3종**이다.

| 줄 | 무엇을 읽는가 | 왜 |
|---|---|---|
| `0a` | `specs/*` (요구사항) | "무엇을 만들어야 하나"의 단일 진실의 원천(source of truth) |
| `0b` | `@IMPLEMENTATION_PLAN.md` | "지금까지 어디까지 왔나" — 이전 반복의 메모리 |
| `0c` | `src/*` 위치 안내 | 실제 코드 어디 있는지 |

`@` 기호는 Claude Code가 자동으로 그 파일을 컨텍스트에 첨부하라는 지시(IDE처럼 동작).

> **핵심 트릭**: 매 반복마다 컨텍스트가 새로 시작하므로 LLM은 "내가 누구지? 뭘 하던 중이지?"부터 시작한다. `0a-0c`가 그 답을 강제로 주입. **상태는 LLM 메모리가 아니라 파일에**.

#### `up to 500 parallel Sonnet subagents` — 비동기 부채꼴 분산(fan-out)

`0a`의 "500개 병렬 서브에이전트"는 단순 강조가 아니라 실제 명령:

- 메인 Opus가 사양 파일들을 직접 다 읽으면 컨텍스트 윈도우 폭발.
- "Sonnet 서브에이전트 500개에게 사양 파일 하나씩 줘서 요약 받아 와" → 메인 컨텍스트는 요약본만 보유.
- **메인 컨텍스트 윈도우 보호 = Ralph가 무한 루프 가능한 이유**.

> **연결**: ghuntley.com/ralph 의 *"Ralph requires a mindset of not allocating to the primary context window. Instead, spawn subagents."* 의 실전 구현이 이 줄.
>
> 한국어 풀이: **"Ralph는 메인 컨텍스트 윈도우에 무엇이든 할당하지 않는 마음가짐을 요구한다. 대신 서브에이전트를 띄워라."**

#### `1` — "choose the most important item" — 결정권을 LLM에게 위임

```
Follow @IMPLEMENTATION_PLAN.md and choose the most important item to address.
```

이게 **반복당 1태스크 원칙**의 실제 메커니즘. 사람이 우선순위를 정하지 않고 LLM이 매번 "지금 가장 중요한 한 개"를 골라 처리. 그 결과가 `IMPLEMENTATION_PLAN.md`에 반영되고 다음 반복의 LLM이 그걸 보고 또 한 개 고름.

**우선순위 결정도 루프의 일부**. 사람은 Ctrl+C만 누른다.

#### `Before making changes, search the codebase (don't assume not implemented)` — 환각 방지 강제

LLM이 "이 함수 없을 것 같으니 만들자"라고 환각해서 중복 구현하는 경우가 잦음. 이 한 줄이 그걸 차단:
- 검색 먼저 → 결과 보고 → 그 다음 작성.

이건 Ralph 특유가 아니라 일반적 에이전트 운영 규칙이지만, **매 반복마다 컨텍스트가 새로 시작하는 Ralph에서는 특히 위험**(이전 반복 기억이 0이라 구현된 것을 또 구현할 위험 ↑). 그래서 명시적으로 박아둔 것.

#### `up to 500 parallel ... only 1 Sonnet subagent for build/tests` — 동시성 제한의 비대칭

검색/읽기는 500 동시, 빌드/테스트는 **1개**. 이유:
- 빌드/테스트는 파일시스템·포트·DB를 공유 → 동시 실행하면 경쟁 조건(race condition).
- 검색은 읽기 전용(read-only) → 안전.

> **읽어낸 의도**: "서브에이전트를 부채꼴 분산할 때 입출력(IO) 안전성 기준으로 한도를 다르게 잡는다." 단순한 성능 튜닝이 아니라 정합성 가드(보호 장치).

#### `4. ... git add -A then git commit ... git push` — LLM이 직접 git 조작

매 반복 안에서 LLM이 commit + push를 한다. `loop.sh`의 마지막 push와 별개.

- 한 반복이 여러 작업 단위로 분할될 수도 있고 → LLM이 의미 단위로 commit.
- `loop.sh`의 마지막 push는 안전망(LLM이 push 잊었을 경우).

이중 push 구조 = "LLM이 빠뜨려도 외부 스크립트가 보장".

#### `99999, 999999, ...` — 9의 개수가 점점 늘어나는 우선순위

```
99999. Important: When authoring documentation, capture the why
999999. Important: Single sources of truth
9999999. As soon as there are no build or test errors create a git tag
...
999999999999999. IMPORTANT: Keep @AGENTS.md operational only
```

처음 봤을 때는 농담 같지만 **의도된 디자인**으로 추정:

1. **시각적 우선순위**: 9가 많을수록 "이건 진짜 중요"라는 신호.
2. **번호 충돌 회피**: 일반 1, 2, 3, 4 사이에 끼우면 절차로 오해됨. `99999`는 "절차의 일부가 아니라 항상 적용되는 메타 규칙(metarule)"임을 강조.
3. **LLM이 잘 따른다**: 중요도 신호로 작동한다는 ghuntley의 경험적 발견. ([ghuntley.com/ralph](https://ghuntley.com/ralph/) 본문 참조)

> **개인적 의문**: 9의 개수가 정확히 의미를 갖나 vs 그냥 점점 끝쪽 = 점점 중요? 후자에 가까워 보임. "끝쪽 메타 규칙"이라는 슬롯 자체가 핵심이고, 9의 개수는 그 슬롯들이 충돌 안 나게 정렬하는 트릭.

#### 마지막 규칙 — `Keep @AGENTS.md operational only`

```
A bloated AGENTS.md pollutes every future loop's context.
```

→ 한국어 풀이: **부풀어 오른 AGENTS.md는 미래의 모든 루프 컨텍스트를 오염시킨다.**

**AGENTS.md는 매 반복 컨텍스트에 자동 주입**되는 파일이다(Claude Code 관례). 그래서 거기에 잡다한 진행 메모를 쓰면 새 컨텍스트도 무용지물 — 매 반복마다 잡음(noise)을 새로 마주하게 됨.

→ AGENTS.md는 **불변에 가까운 운영 규칙**, IMPLEMENTATION_PLAN.md는 **휘발성 작업 메모**. 컨텍스트 위생을 위한 분리.

> **연결**: §4 AGENTS.md가 왜 그렇게 짧은지 이 규칙으로 설명됨.

## 3. `PROMPT_plan.md` — 빌드와 다른 인지 모드

### 3-A. 전체 원본 텍스트

```
0a. Study `specs/*` with up to 250 parallel Sonnet subagents to learn the application specifications.
0b. Study @IMPLEMENTATION_PLAN.md (if present) to understand the plan so far.
0c. Study `src/lib/*` with up to 250 parallel Sonnet subagents to understand shared utilities & components.
0d. For reference, the application source code is in `src/*`.

1. Study @IMPLEMENTATION_PLAN.md (if present; it may be incorrect) and use up to 500 Sonnet subagents
   to study existing source code in `src/*` and compare it against `specs/*`. Use an Opus subagent
   to analyze findings, prioritize tasks, and create/update @IMPLEMENTATION_PLAN.md as a bullet
   point list sorted in priority of items yet to be implemented. Ultrathink. Consider searching
   for TODO, minimal implementations, placeholders, skipped/flaky tests, and inconsistent patterns.

IMPORTANT: Plan only. Do NOT implement anything. Do NOT assume functionality is missing;
confirm with code search first. Treat `src/lib` as the project's standard library for shared
utilities and components. Prefer consolidated, idiomatic implementations there over ad-hoc copies.

ULTIMATE GOAL: We want to achieve [project-specific goal]. Consider missing elements and plan
accordingly. If an element is missing, search first to confirm it doesn't exist, then if needed
author the specification at specs/FILENAME.md.
```

### 3-B. build와의 차이

| 항목 | PROMPT_build.md | PROMPT_plan.md |
|---|---|---|
| 동시 서브에이전트 | 500 | 250 |
| 핵심 동사 | `implement`(구현) | `plan`(계획) |
| 결과물 | 코드 + 테스트 + 커밋 | `IMPLEMENTATION_PLAN.md` 갱신 + (선택) 새 사양 작성 |
| 굵은 금지문구 | 없음 | **`Plan only. Do NOT implement anything.`** ("계획만 해라. 아무것도 구현하지 말라.") |
| `src/lib` 별도 처리 | 없음 | `0c`에서 250개 서브에이전트로 별도 학습 |

#### 3-B-1. `Plan only` — 모드 분리의 이유

LLM은 자연스럽게 "분석 → 즉시 구현"으로 미끄러진다. 계획 모드에서 그게 발생하면 **계획 없이 휘갈긴 코드**가 누적됨. 그래서 명시적 금지.

> **읽어낸 의도**: "생각하는 루프"와 "실행하는 루프"를 분리. 사람이 `./loop.sh plan`으로 며칠 돌리고 IMPLEMENTATION_PLAN이 안정되면 `./loop.sh`로 빌드 시작.

#### 3-B-2. 동시성이 절반인 이유 (500 → 250)

빌드 모드는 파일을 새로 쓰니까 부채꼴 분산 후 결과 합치기가 쉽다 (각자 다른 파일). 계획 모드는 **500개 분석 결과를 하나의 우선순위 목록으로 머지(병합)**해야 함. 머지 비용을 고려해 부채꼴 분산을 보수적으로.

#### 3-B-3. `[project-specific goal]` 자리표시자(placeholder)

```
ULTIMATE GOAL: We want to achieve [project-specific goal].
```

이 부분만 사용자가 매번 채워 넣어야 하는 슬롯. 나머지 프롬프트 본문은 프로젝트 무관하게 재사용 가능. **재사용 가능한 골격 + 한 슬롯**이 ghuntley 패턴의 표준 형식.

## 4. `AGENTS.md` — 의도적으로 짧은 운영 규칙

### 4-A. 전체 원본 텍스트

```markdown
## Build & Run

Succinct rules for how to BUILD the project:

## Validation

Run these after implementing to get immediate feedback:

- Tests: `[test command]`
- Typecheck: `[typecheck command]`
- Lint: `[lint command]`

## Operational Notes

Succinct learnings about how to RUN the project:

...

### Codebase Patterns

...
```

### 4-B. 빈 섹션의 의미

`...` 가 그대로 들어가 있다 — 자리표시자가 아니라 **"여기는 LLM이 채워라"라는 의도된 공백**.

PROMPT_build.md의 규칙:

> *9999999999. When you learn something new about how to run the application, update @AGENTS.md using a subagent but keep it brief.*
>
> 한국어 풀이: **애플리케이션을 실행하는 법에 대해 새로 배운 게 있으면 서브에이전트를 통해 @AGENTS.md를 갱신해라. 단 간결하게.**

→ 매 반복에서 LLM이 `npm test` 같은 명령을 실패시킨 뒤 올바른 명령(`pnpm test`)을 학습하면 **여기에 직접 쓴다**.

> **핵심 관찰**: AGENTS.md는 사람의 문서가 아니라 **LLM의 자기 메모**. 매 반복마다 새 컨텍스트로 시작하는 다음 반복 LLM에게 "이 프로젝트에선 `pnpm test`야"라고 알려주는 인계장.

### 4-C. AGENTS.md vs IMPLEMENTATION_PLAN.md의 분리

PROMPT_build.md 마지막 줄:

> *Keep @AGENTS.md operational only — status updates and progress notes belong in IMPLEMENTATION_PLAN.md. A bloated AGENTS.md pollutes every future loop's context.*
>
> 한국어 풀이: **@AGENTS.md는 운영 정보만 유지해라. 상태 업데이트와 진척 메모는 IMPLEMENTATION_PLAN.md에 속한다. 부풀어 오른 AGENTS.md는 미래의 모든 루프 컨텍스트를 오염시킨다.**

| 파일 | 무엇을 담나 | 왜 |
|---|---|---|
| `AGENTS.md` | "이 프로젝트는 이렇게 빌드/테스트한다" — **불변 사실** | 매 반복 자동 주입, 짧아야 함 |
| `IMPLEMENTATION_PLAN.md` | "지금 이 작업이 진행 중" — **휘발성 상태** | 매 반복 갱신, 길어도 됨 (필요 시 LLM이 정리) |

이 분리가 **새 컨텍스트 시작 방식의 효율을 결정**. AGENTS.md가 부풀면 매 반복 토큰 낭비, IMPLEMENTATION_PLAN.md는 어차피 명시적 읽기 단계(0b)에서 한 번만 읽음.

## 5. `IMPLEMENTATION_PLAN.md` — 한 줄짜리 자가 진화 파일

### 5-A. 전체 원본 텍스트

```
<!-- Generated by LLM with content and structure it deems most appropriate -->
```

→ 한국어 풀이: **(LLM이 가장 적절하다고 판단한 내용과 구조로 생성됨)**

진짜 한 줄. 끝.

### 5-B. 의도

이 파일은 ghuntley가 **구조를 정의하지 않음**. PROMPT_build.md / PROMPT_plan.md가 이 파일을 어떻게 쓸지 약 7번 언급:

- `0b. Study @IMPLEMENTATION_PLAN.md` (읽기)
- `1. Follow @IMPLEMENTATION_PLAN.md and choose the most important item` (소비)
- `3. immediately update @IMPLEMENTATION_PLAN.md with your findings` (덧붙이기)
- `4. update @IMPLEMENTATION_PLAN.md, then git add -A then git commit` (커밋)
- `999999999. Keep @IMPLEMENTATION_PLAN.md current with learnings` (유지)
- `99999999999. document them in @IMPLEMENTATION_PLAN.md` (버그 기록)
- `9999999999999. periodically clean out the items that are completed` (청소)

→ LLM이 "읽기-수정-커밋" 사이클로 진화시키되, **형식은 LLM이 매 반복마다 더 좋아 보이는 쪽으로 자율 결정**.

> **흥미로운 발견**: 사람은 형식(JSON 스키마, 프론트매터 등)을 강요할 수 있지만 ghuntley는 안 한다. 이유 추정 — 형식을 정하면 LLM이 그 형식에 맞추느라 정작 중요한 정보를 못 적는 경우가 발생. 자유로운 마크다운 쪽이 정보 손실이 적다는 경험적 결론.

> **반론 가능**: "구조 없으면 LLM마다 다르게 써서 다음 반복 LLM이 헷갈리지 않나?" → 매 반복마다 새 컨텍스트니까 직전 LLM이 만든 형식을 그대로 보고 따라 쓸 가능성이 큼. 결과적으로 어떤 안정 구조가 자연 발생(emerge)한다는 가설.

## 6. 통합 메커니즘 — 5개 파일이 합쳐서 만드는 루프

```
                          ┌─────────────────────────────────┐
                          │           loop.sh               │
                          │     while true; do ... done     │
                          └────────────┬────────────────────┘
                                       │ cat PROMPT_*.md | claude -p
                                       ▼
                ┌──────────────────────────────────────────┐
                │  새 Claude (Opus) 프로세스               │
                │  컨텍스트 = PROMPT_*.md (만)             │
                └────────────┬─────────────────────────────┘
                             │
            ┌────────────────┼────────────────┬────────────────────┐
            ▼                ▼                ▼                    ▼
     specs/* 읽기       AGENTS.md 읽기   IMPL_PLAN.md 읽기   src/* 읽기
     (서브에이전트 500) (자동 첨부)     (과거 메모리)       (부채꼴 분산)
            │                │                │                    │
            └────────────────┴────────┬───────┴────────────────────┘
                                      ▼
                          ┌───────────────────────┐
                          │  최우선 작업 선택     │
                          │  구현. 테스트.        │
                          │  커밋. push.          │
                          └───────────┬───────────┘
                                      │
                  ┌───────────────────┼─────────────────┐
                  ▼                   ▼                 ▼
         IMPL_PLAN 갱신        AGENTS 갱신          git push
         (작업 결과)           (학습한 명령)        (체크포인트)
                  │                   │                 │
                  └───────────────────┴─────────────────┘
                                      │
                          ┌───────────────────────┐
                          │  Claude 종료          │
                          │  (stop_reason: end)   │
                          └───────────┬───────────┘
                                      │
                                      ▼
                          ┌───────────────────────┐
                          │ loop.sh `git push`    │
                          │ (안전망)              │
                          └───────────┬───────────┘
                                      │
                                      ▼
                          ┌───────────────────────┐
                          │  ITERATION+=1         │
                          │  while true 재진입    │
                          └───────────────────────┘
```

### 6-A. 종료 조건은 어디 있나?

답: **명시적 종료 조건이 없다**. 가능한 종료 경로:

1. `MAX_ITERATIONS` 도달 (선택적, 기본 0=무한)
2. `Ctrl+C` (사람)
3. `cat PROMPT.md` 가 실패 (파일 삭제)

**LLM이 "끝났다"고 선언할 권한이 없다**. 이게 §0의 README 7장 인용 *"Ralph 원본 종료 조건: '종료 조건이 없다. 사람이 Ctrl+C 누르거나 fix_plan.md가 빌 때까지'"* 의 코드 수준 증거.

### 6-B. "매 반복마다 새 컨텍스트"가 의미하는 것

매 `cat PROMPT.md | claude -p` 호출은 **새 프로세스**. 이전 반복의:
- ❌ 대화 기록(history)
- ❌ 메모리상 가설
- ❌ 잘못 추론한 가정

전부 사라진다. 살아남는 것은 **파일시스템 + git** 뿐.

→ 이 설계가 LLM의 "긴 대화에서 망가지는 주의력(attention)" 문제를 회피.

> **연결**: README §3-A의 *"매 반복마다 새 컨텍스트(이게 핵심 원칙)"* 는 단순 표어가 아니라 **bash 한 줄 (`while ...; do cat ... | claude -p`) 의 구조적 결과**. `claude` 프로세스가 매번 새로 뜨니까.

### 6-C. "Ralph는 monolithic" — 단일 저장소 단일 프로세스

ghuntley.com/ralph 인용:
> *"Ralph is monolithic. Ralph works autonomously in a single repository as a single process that performs one task per loop."*
>
> 한국어 풀이: **Ralph는 단일체(monolithic)다. 단일 저장소에서 단일 프로세스로 자율적으로 동작하며, 루프당 작업 하나를 처리한다.**

코드 수준 증거:
- `loop.sh`는 단일 저장소의 현재 작업 디렉토리(cwd)에서만 동작
- 한 번에 하나의 `claude` 프로세스만 (병렬 아님)
- 한 반복에 한 태스크 (`choose the most important item to address`)

분산이 아니다. 의도적으로 단순.

> **개인적 의문**: 그러면 여러 태스크를 동시 진행하려면? → 다른 작업트리(worktree)에서 별도 ralph 인스턴스 띄우면 됨. 즉 "Ralph를 분산"이 아니라 "여러 Ralph를 띄움". 단순함이 분산의 단위.
