관측 저장소의 인덱스와 압축 알고리즘

ClickHouse, VictoriaLogs, Prometheus가 적은 디스크로 빠르게 찾는 데 쓰는 네 가지 알고리즘입니다. 탭마다 실제로 비트, 인덱스, 블록이 어떻게 움직이는지 단계별로 재생합니다.

Bloom filter: "확실히 없음"을 싸게 알아낸다

비트 배열 m개와 해시 함수 k개로 집합을 표현합니다. 넣을 때는 k개 위치를 1로 켜고, 확인할 때는 k개 위치가 모두 1인지 봅니다. 하나라도 0이면 넣은 적이 없다는 게 확실하고, 모두 1이면 "있을 수도" 있습니다. 원본 값은 저장하지 않아서 아주 작습니다.

쓰이는 곳 · VictoriaLogs 블록별 토큰 필터, ClickHouse bloom_filter skip index, RocksDB SSTable, Cassandra

 
넣은 값

왜 효율적인가

  • 원소당 약 10비트면 false positive가 약 1%입니다. 단어 길이와 상관없이 크기가 고정됩니다.
  • false positive 확률 p ≈ (1 − e−kn/m)k, 가장 좋은 k = (m/n)·ln 2 입니다. 값을 많이 넣을수록 1이 늘어 오탐이 많아집니다.
  • "없음"은 틀리지 않습니다. 그래서 블록을 건너뛰는 용도에 맞습니다. "있음"은 결국 블록을 읽어서 확인합니다.
  • 해시 k개는 h1 + i·h2 방식으로 두 해시에서 만듭니다 (Kirsch–Mitzenmacher). 이 페이지도 같은 방식입니다.
  • 원소를 지울 수 없습니다. 불변 블록·part마다 하나씩 만드는 구조와 잘 맞습니다.

Sparse primary index: 행이 아니라 granule을 가리킨다

ClickHouse part는 ORDER BY (service, ts)로 정렬되어 있고, 행을 granule 단위(기본 8192행, 여기선 6행)로 묶습니다. primary index는 각 granule 첫 행의 키만 저장합니다. 인덱스가 작아서 메모리에 전부 올라가고, 이진 탐색으로 읽을 granule 범위를 고릅니다.

쓰이는 곳 · ClickHouse primary.idx + 컬럼별 mark 파일, VictoriaLogs 블록 헤더의 시간 범위, LSM SSTable의 index block

primary.idx · granule마다 키 1개
part 데이터 · service · ts · status

왜 효율적인가

  • 1억 행 part도 인덱스 항목은 1억 ÷ 8192 ≈ 12,200개뿐입니다. B-tree처럼 행마다 항목을 두지 않습니다.
  • 데이터가 정렬되어 있으니 "이 키는 이 granule 사이에 있다"만 알면 충분합니다. 결과는 granule 단위라 약간 더 읽지만 순차 읽기입니다.
  • 정렬 키의 앞쪽 컬럼일수록 잘 걸러집니다. 정렬 키에 없는 컬럼은 전체를 읽어야 해서 skip index(minmax, set, bloom_filter, text)로 보완합니다.
  • mark 파일은 granule 번호를 컬럼 파일 안의 위치(압축 블록 오프셋, 블록 안 오프셋)로 바꿔 줍니다. 필요한 컬럼의 필요한 granule만 읽습니다.

역인덱스: 토큰에서 행 번호로

로그를 토큰으로 자르고, 토큰마다 그 토큰이 나온 행 번호 목록(posting list)을 저장합니다. 검색은 토큰의 posting list를 찾아 교집합(AND)이나 합집합(OR)을 구하면 끝입니다. bloom filter가 "이 블록엔 없다"를 알려 준다면, 역인덱스는 "이 행들에 있다"를 알려 줍니다.

쓰이는 곳 · ClickHouse text index (26.2부터 GA, hasAllTokens · hasAnyTokens), Elasticsearch/Lucene, Loki는 쓰지 않음 (라벨만 인덱싱)

로그 행 · 2행씩 블록
사전 · 토큰 → posting list

왜 효율적인가

  • 검색 비용이 전체 로그 양이 아니라 posting list 길이에 비례합니다. 드문 토큰일수록 빠릅니다.
  • posting list는 정렬된 정수 목록이라 차이값(delta) + 비트 패킹이나 Roaring bitmap으로 아주 작게 압축됩니다.
  • 교집합은 정렬된 목록 두 개를 동시에 훑는 방식으로 O(a+b)에 끝납니다.
  • 대가는 인덱스 크기와 쓰기 비용입니다. bloom filter는 작지만 "있을 수도"인 블록을 전부 읽어야 합니다.
  • 토크나이저가 결과를 정합니다. user_42를 한 토큰으로 볼지 둘로 볼지에 따라 검색되는 것이 달라집니다.

Gorilla 압축: 타임스탬프는 delta-of-delta, 값은 XOR

Facebook Gorilla 논문(2015)의 방식입니다. 샘플 하나는 원래 타임스탬프 64비트 + float64 값 64비트 = 128비트입니다. 수집 간격이 일정하면 delta의 delta는 거의 0이고, 값이 천천히 변하면 이전 값과 XOR한 결과는 대부분 0 비트입니다. 둘 다 0을 1비트로 적어서 크기를 크게 줄입니다.

쓰이는 곳 · Prometheus TSDB chunk (같은 원리, 타임스탬프 구간 비트 수는 다름), ClickHouse CODEC(DoubleDelta) · CODEC(Gorilla), InfluxDB. VictoriaMetrics는 값을 정수로 바꾼 뒤 다른 방식으로 압축

#t (초)ΔΔΔt 인코딩비트값이전 값 XOR (64비트)값 인코딩비트

인코딩 규칙 (논문 기준)

  • 타임스탬프 ΔΔ = 0 → 0 (1비트). [−63, 64] → 10+7비트, [−255, 256] → 110+9비트, [−2047, 2048] → 1110+12비트, 그 밖 → 1111+32비트. 첫 Δ는 14비트.
  • 값 XOR = 0 → 0 (1비트). 0이 아니면 앞쪽 0 개수와 뒤쪽 0 개수를 보고, 이전 블록 범위 안에 들어가면 10+의미 있는 비트만, 아니면 11+앞쪽 0 개수(5비트)+길이(6비트)+의미 있는 비트.
  • 논문의 실제 데이터에서 평균 1.37바이트/샘플 (원래 16바이트). Prometheus는 밀리초 타임스탬프라 구간을 14 · 17 · 20비트로 넓혀 씁니다.
  • 값이 무작위로 흔들리면 XOR 결과에 의미 있는 비트가 많아져 압축이 거의 안 됩니다. "랜덤 소수"를 골라 비교해 보세요.
