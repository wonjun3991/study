## 슬라이드 2: 오늘의 두 축

**예상 시간**: 1분

이 표 한 장만 머리에 남기고 가셔도 됩니다. 자기 정보는 Downward API로, 남의 정보는 API 서버 호출로 받습니다. 결정적 차이는 **외부 통신 여부**입니다.

Downward API는 컨테이너가 시작될 때 kubelet이 환경변수나 파일로 정보를 주입해주는 방식입니다. 네트워크 호출이 일어나지 않아요. 반면 다른 리소스를 조회하려면 반드시 API 서버에 HTTPS 요청을 보내야 하고, 인증과 인가도 통과해야 합니다.

이 두 가지를 헷갈려서 모든 정보를 API 호출로 받으려고 하는 분들이 있는데, 자기 Pod 이름 같은 건 Downward API로 받는 게 압도적으로 가볍고 안전합니다.

**강조**: 외부 통신 여부 = 결정적 차이
**다음 슬라이드 연결**: "그런데 그 전에, 우리가 정말 Pod을 직접 만드나요?"

## 슬라이드 3: 잠깐, 우리는 Pod을 직접 만들지 않는다

**예상 시간**: 1분 15초

이 슬라이드는 챕터 본론으로 들어가기 전에 **왜 이 챕터가 중요한지**를 짚는 슬라이드입니다.

여러분, 실무에서 Pod manifest를 직접 작성해 본 분 계신가요? 거의 없을 겁니다. 우리가 보통 작성하는 건 Deployment YAML 한 장이죠. `replicas: 3`이라고 적으면 끝입니다.

그러면 무슨 일이 일어나냐, 이 그림처럼 4단계 위임이 일어납니다. **Deployment**가 원하는 상태를 선언하면, **ReplicaSet**이 그 개수를 맞추고, **Pod**이 실제 스케줄링되어 **Container**가 뜹니다. 각 단계는 자기 책임만 집니다 — Deployment는 "버전 관리", ReplicaSet은 "개수 관리", Pod은 "스케줄링", Container는 "프로세스".

여기서 중요한 건 **Pod 이름이 매번 다르다**는 점이에요. ReplicaSet이 자동으로 만들면서 `kubia-7d4b8c9f-x7k2n` 같이 hash가 붙습니다. 우리가 정한 게 아닙니다. 자기 IP도 마찬가지로 스케줄링되어야 결정되고요.

그래서 **앱은 자기 Pod 이름을 미리 알 수 없습니다**. 실행 시점에 받아야 합니다. 그게 바로 Downward API가 필요한 이유입니다.

**강조**: Pod은 자동 생성됨 → 이름·IP는 매번 다름 → 실행 시점에 알아야 함
**다음 슬라이드 연결**: "그럼 본격적으로 첫 번째 주제, Downward API로 갑시다."

> _참고_: ownerReferences로 이 계층 구조가 표현됩니다. Pod은 자기 ownerReferences로 ReplicaSet을 가리키고, ReplicaSet은 Deployment를 가리킵니다. 자세한 동작은 ch04(ReplicationController)와 ch09(Deployment)에서 다룹니다.

## 슬라이드 5: 왜 Downward API가 필요한가?

**예상 시간**: 1분 30초

세 가지 시나리오를 보겠습니다.

첫째, 로깅. 마이크로서비스에서 "어느 Pod이 이 요청을 처리했지?"를 알아야 디버깅이 가능합니다. 그런데 앱 코드는 자기 Pod 이름을 모릅니다. 컨테이너 안에서 `hostname` 명령을 치면 Pod 이름이 나오긴 하는데, 그건 우연이고 보장된 건 아닙니다.

둘째, 메트릭. JVM 앱이 자기 메모리 limit을 알면 Heap 사이즈를 자동으로 맞출 수 있습니다. CPU limit으로 스레드 풀 크기를 정할 수도 있고요.

셋째, 분산 시스템. 자기 IP를 알아야 다른 노드와 클러스터링할 수 있는 경우가 있습니다.

이런 정보를 받으려고 매번 k8s API에 요청 보내는 건 **너무 무겁습니다**. 그래서 kubelet이 컨테이너 시작 시점에 이 정보들을 환경변수나 파일로 주입해주는 거죠.

**강조**: k8s 의존도를 낮추는 것도 핵심 — 환경변수로 받으면 다른 환경에서도 같은 코드 사용 가능.
**다음 슬라이드 연결**: "주입 방법은 두 가지가 있습니다."

## 슬라이드 6: 노출 방법 두 가지

**예상 시간**: 1분

방법 1, **환경변수**. 컨테이너 spec의 env에 `valueFrom` 블록으로 정의합니다. 가장 흔하게 쓰입니다.

방법 2, **`downwardAPI` 볼륨**. 볼륨을 마운트하는 형태인데, 파일 하나에 필드 하나를 노출합니다.

차이는 두 가지입니다.

첫째, **변경 반영 시점**. 환경변수는 컨테이너 시작 시 한 번 설정되고 끝입니다. 라벨이 바뀌어도 환경변수는 갱신 안 됩니다. 볼륨은 일부 필드가 런타임에 자동 갱신됩니다.

둘째, **표현할 수 있는 범위**. 멀티라인 값, 예를 들어 라벨 전체나 어노테이션 전체는 환경변수로 못 받습니다. 볼륨만 가능해요.

**강조**: 단순 식별자는 env, 풍부한 정보는 volume
**다음 슬라이드 연결**: "구체적으로 어떤 필드들이 가능한지 보겠습니다."

## 슬라이드 7: fieldRef 노출 가능 필드

**예상 시간**: 1분 30초

이 슬라이드는 외울 필요 없고, 패턴만 기억하면 됩니다.

**둘 다 가능한 것**: Pod의 기본 식별자들 — 이름, 네임스페이스, UID. 그리고 라벨이나 어노테이션의 **단일 키**. 예를 들어 `metadata.labels['app']`처럼 키 하나만 뽑는 건 환경변수로 가능합니다.

**환경변수 전용**: nodeName, podIP, serviceAccountName 같은 단일 값 필드들. 의외로 많아요. 볼륨으로는 안 됩니다.

**볼륨 전용**: 단 두 개. **전체** labels와 **전체** annotations. 멀티라인이라 환경변수에 못 넣어요.

여기서 책의 1판 노트와 다른 점 하나. 책에는 "labels는 env 불가"라고 되어 있는데, 이건 정확히는 **전체 labels가 env 불가**입니다. 단일 키는 가능합니다. 공식 문서를 직접 봐야 알 수 있는 디테일이에요.

또 책 시점에는 없던 `status.podIPs`, `status.hostIPs`도 추가됐습니다. 듀얼스택, 즉 IPv4와 IPv6를 동시에 받는 환경에서 쓰는 슬라이스 형태죠.

**강조**: 전체 라벨은 volume만, 단일 키는 env도 가능
**다음 슬라이드 연결**: "리소스 정보는 또 다른 방식으로 받습니다."

## 슬라이드 8: resourceFieldRef

**예상 시간**: 1분 30초

리소스, 그러니까 CPU나 메모리 정보는 `resourceFieldRef`로 받습니다.

핵심은 `divisor`입니다. 예를 들어 CPU request가 100m으로 설정돼 있을 때, divisor를 `1m`으로 주면 환경변수 값이 "100"으로 들어옵니다. divisor 없이 받으면 "0.1"이 들어와요. 정수만 받고 싶으면 divisor를 명시해야 합니다.

메모리는 `1Mi`, `1Gi` 같은 단위로 변환할 수 있습니다.

면접에서 가끔 묻는 트릭 질문: "limits.cpu가 100m인데 divisor 없으면 값이 뭐냐?" 답은 "0.1"입니다. 반올림되는 게 아니라 그대로 소수점이 나와요.

`hugepages-*`는 DPDK 쓰는 네트워크 앱이나 JVM Large Pages를 쓸 때만 필요합니다. 일반적인 워크로드에서는 신경 안 써도 됩니다.

**강조**: divisor가 단위 변환의 핵심
**다음 슬라이드 연결**: "실제로 env에 어떻게 주입하는지 보겠습니다."

## 슬라이드 9: env로 주입하는 예시

**예시 시간**: 1분

가장 흔한 패턴 세 개입니다.

`POD_NAME`은 로깅용. 모든 로그에 이걸 찍으면 어느 Pod에서 나온 건지 추적할 수 있습니다.

`POD_IP`는 자기 IP. 분산 캐시 같은 데서 자기 노드를 식별할 때 씁니다.

`NODE_NAME`은 어느 워커 노드에 떠있나. 디버깅용으로 매우 유용합니다. "이 노드에서만 문제가 생기네?" 같은 패턴 발견에 도움이 됩니다.

3-tier 구조 — `valueFrom` → `fieldRef` → `fieldPath` — 이건 외워두면 좋아요. 거의 모든 매니페스트에서 같은 패턴이 반복됩니다.

**강조**: valueFrom + fieldRef + fieldPath — 3-tier 패턴
**다음 슬라이드 연결**: "이번엔 볼륨으로 주입하는 방법입니다."

## 슬라이드 10: 볼륨으로 주입

**예상 시간**: 1분

볼륨 방식은 마운트 포인트에 파일이 자동 생성되는 형태입니다. 여기서 `path`는 파일 이름이고, `fieldRef`로 어떤 필드를 노출할지 지정합니다.

핵심은 `metadata.labels`를 통째로 노출할 수 있다는 거예요. 환경변수로는 못 했던 것이죠. `/etc/downward/labels` 파일을 열면 이런 식으로 자동 포맷됩니다:
```
app="kubia"
env="prod"
```
한 줄에 키=값 형태로 정렬돼서 들어와요.

앱이 이 파일을 watch하면 라벨 변경을 실시간으로 감지할 수 있습니다. 이게 다음 슬라이드의 핵심입니다.

**강조**: 멀티라인은 volume, 파일 형식은 자동 포맷
**다음 슬라이드 연결**: "여기서 진짜 인사이트가 나옵니다."

## 슬라이드 11: 핵심 차이 — 런타임 갱신

**예상 시간**: 2분

이 슬라이드가 8장 전체에서 **가장 실용적인 인사이트**입니다.

환경변수는 컨테이너 시작할 때 한 번 설정되고 끝입니다. 라벨이 바뀌어도, CPU limit이 바뀌어도 환경변수는 그대로 stale한 채로 남아있습니다. 갱신하려면 컨테이너 재시작.

볼륨은 살아있는 파일이에요. k8s가 백그라운드에서 갱신해줍니다.

실제로 검증해봤습니다. `kubectl label pod kubia env=production` 하고 컨테이너 안에서 5초 정도 기다리면 `/etc/downward/labels` 파일이 자동으로 바뀌어 있습니다. Pod 재시작 없어요.

여기서 v1.35부터 stable이 된 in-place resize가 등장합니다. 컨테이너를 재시작하지 않고 CPU나 메모리 limit을 바꿀 수 있게 됐어요. 이때 볼륨 파일은 자동 갱신, 환경변수는 stale 유지입니다. 그래서 만약 JVM 앱이 limits.memory 보고 Heap을 잡는다면, **반드시 볼륨으로 받아야** 한다는 게 결론입니다. 환경변수로 받으면 리사이즈 후 Heap이 옛날 값에 묶여서 stale해집니다.

**강조**: 리소스 의존 정보는 반드시 volume으로
**다음 슬라이드 연결**: "여기까지가 자기 자신을 아는 법입니다. 두 번째 주제로 넘어가기 전에 두 메커니즘을 직접 비교해보고 가겠습니다."

## 슬라이드 12: 두 메커니즘, 같은 작업 ─ 비용 비교

**예상 시간**: 1분 30초

이 슬라이드는 Part 1과 Part 2 사이의 다리입니다.

같은 정보 — 예를 들어 Pod 이름 — 를 두 방식으로 받았을 때 비용이 어떻게 다른지 직접 비교했습니다.

**왼쪽, Downward API**. 코드는 한 줄입니다. `os.Getenv("POD_NAME")` 또는 `open("/etc/downward/podName").read()`. 네트워크 통신은 0회. 인증도 필요 없어요. 지연은 거의 0입니다 — 메모리에 있거나 로컬 파일 한 번 읽는 거니까요.

**오른쪽, API 서버 호출**. 같은 정보를 받겠다고 하면 코드는 최소 다섯 줄로 늘어납니다. 토큰 읽고, CA 인증서 경로 잡고, Authorization 헤더 만들고, HTTPS 요청 보내고. 네트워크 통신 1회 — Pod에서 kube-proxy를 거쳐 apiserver까지. 인증도 다 통과해야 합니다. 지연은 수십 ms 단위 — 네트워크니까요.

**핵심 메시지**: **할 수만 있으면 항상 Downward API**입니다. API 호출은 "남의 정보"가 꼭 필요할 때만 쓰는 거예요.

청중이 흔히 하는 실수가 있어요:
- Pod name 알겠다고 API 호출 → Downward env로 충분
- 자기 IP 알겠다고 API 호출 → status.podIP fieldRef
- 자기 컨테이너 메모리 limit 알겠다고 API 호출 → resourceFieldRef

이 세 경우 모두 Downward API로 끝낼 수 있습니다. API 호출이 진짜 필요한 건 다른 Pod 목록이나, Service 목록 같은 **남의 정보**일 때입니다.

**강조**: 코드 1줄 vs 5+줄, 통신 0회 vs 1회, 지연 ~0 vs 수십 ms
**다음 슬라이드 연결**: "그럼 그 '남의 정보가 필요한' 진짜 use case부터 봅시다."

## 슬라이드 14: 왜 API 서버 직접 호출?

**예상 시간**: 1분

Downward API로는 안 되는 질문들입니다. 같은 Service 뒤의 다른 Pod IP는? 클러스터의 모든 Service 목록은? 최근 발생한 이벤트는?

이런 정보는 모두 API 서버가 가지고 있고, 직접 쿼리해야 합니다.

대표 use case는 분산 데이터베이스의 peer discovery입니다. Cassandra가 다른 Cassandra 노드 IP를 알아야 클러스터링할 수 있는데, 이걸 K8s API에서 조회합니다. 또 cluster-autoscaler 같은 운영 도구, Operator 패턴이 다 이 방식을 씁니다.

일반 비즈니스 앱에서는 잘 안 쓰지만, 한 번 쓰면 인증 흐름을 정확히 알아야 합니다.

**강조**: 분산 시스템 + Operator 시나리오
**다음 슬라이드 연결**: "어디로 호출해야 하는지부터 보겠습니다."

## 슬라이드 16: 왜 HTTPS인가? ─ Bearer token의 운명

**예상 시간**: 2분

이 슬라이드는 ch12 보안 챕터의 미리보기인데, ch08을 이해하는 데도 꼭 필요합니다. **왜 평문 HTTP가 아니고 HTTPS여야 하는가**.

**왼쪽, HTTP였다면 (가상 시나리오)**. Bearer 토큰은 HTTP 헤더에 평문으로 실립니다. `Authorization: Bearer eyJ...` 이렇게요. HTTP로 전송하면 네트워크 경로 어디서든 이걸 캡처할 수 있어요.

여기서 청중이 흔히 하는 오해 — **"내부 네트워크니까 안전하지 않나요?"**. 아닙니다. Pod에서 apiserver로 가는 트래픽은 노드 간 네트워크를 통과합니다. CNI overlay를 포함해서요. Kubernetes 공식 문서가 명시적으로 그러는데, **"노드와 Pod에서 컨트롤 플레인으로 가는 통신은 untrusted 또는 public 네트워크를 통과하는 것을 가정한다"**고 합니다. 즉 신뢰할 수 없는 네트워크.

토큰이 한 번 탈취되면? **만료 전까지 SA 권한 전체가 노출**됩니다. 공격자가 그 토큰으로 내가 가진 모든 권한을 그대로 사용할 수 있어요. v1.22 이후엔 projected token으로 자동 만료되긴 하지만, 그 사이에도 손해는 충분합니다.

**오른쪽, HTTPS (현재)**. 토큰 헤더가 TLS로 암호화돼서 도청해도 의미 없는 바이트 덩어리입니다. 그리고 `ca.crt`가 하는 일이 또 있어요 — apiserver가 제시한 인증서의 SAN 필드를 검증합니다. SAN에는 `kubernetes.default.svc`, `10.96.0.1` 같은 식별자가 들어있어서, **MITM이 가짜 인증서로 끼어들면 검증이 실패해서 연결이 끊깁니다**.

역사적 사실 하나. 옛날엔 `--insecure-port=8080`으로 평문 HTTP를 띄울 수 있었어요. 인증 우회 포트였죠. v1.10에 deprecated 됐고, **v1.20에 코드 자체가 제거**됐습니다. v1.24에선 플래그도 없어졌어요. 지금 클러스터에선 평문으로 띄우는 게 **물리적으로 불가능**합니다.

추가 질문 가능성: "왜 mTLS 안 쓰고 Bearer token이냐?" → Pod은 동적이라 인증서 사전 발급이 어려워요. JWT는 SA가 자동 발급하고 자동 만료시키니 운영이 편합니다. 다만 KEP-4317 "Pod Certificates"가 v1.35 베타에 있어서 곧 빌트인 mTLS 지원이 생길 예정입니다.

**강조**: 평문 토큰 = 즉시 SA 권한 탈취 / HTTPS = 토큰 암호화 + SAN 검증으로 MITM 차단
**다음 슬라이드 연결**: "그럼 이제 그 인증 메커니즘을 자세히 봅시다 — ServiceAccount 토큰."

## 슬라이드 17: 인증 — ServiceAccount

**예상 시간**: 1분 30초

모든 Pod에는 자동으로 ServiceAccount 정보가 마운트됩니다. 경로는 `/var/run/secrets/kubernetes.io/serviceaccount/`고, 거기에 세 파일이 있어요.

`token`이 JWT Bearer 토큰으로 인증에 쓰입니다. `ca.crt`는 API 서버의 TLS 인증서를 검증하는 데 쓰고요. `namespace`는 편의용 — 자기 네임스페이스가 어딘지 알려줍니다.

이 마운트는 ServiceAccount admission controller가 자동으로 해줍니다. 명시적으로 끄려면 `automountServiceAccountToken: false`를 Pod spec에 넣으면 됩니다.

요즘 클러스터(1.21 이상)는 **Projected Token** 방식이에요. 책 시점의 영구 토큰과 달리 만료 시간이 있고, 감사가 가능합니다. 보안적으로 훨씬 좋습니다.

**강조**: token + ca.crt + namespace 3종 세트
**다음 슬라이드 연결**: "실제 호출이 어떻게 생겼는지 보겠습니다."

## 슬라이드 19: RBAC 벽

**예상 시간**: 1분 30초

`default` ServiceAccount는 아무 권한도 없습니다. K8s 1.6 이후로 디폴트가 deny입니다.

해결은 Role과 RoleBinding 두 개입니다.

Role은 "이런 권한이 있다"는 정의예요. 여기 예시는 core API group에서 pods 리소스를 get/list 할 수 있다는 의미입니다.

RoleBinding은 "이 권한을 누구에게 준다"는 매핑이고요. 여기서는 default ServiceAccount에게 Role을 연결하는 거죠.

ClusterRole/ClusterRoleBinding은 클러스터 전역에 적용되고, Role/RoleBinding은 한 네임스페이스에만 적용됩니다. 권한 범위를 좁히는 게 좋으니 가능하면 네임스페이스 단위로.

**강조**: 권한은 명시적으로 부여, 디폴트는 거부
**다음 슬라이드 연결**: "실습에서 이걸 5단계로 검증했습니다."

## 슬라이드 20: 실습 5단계 검증

**예상 시간**: 2분

실제로 클러스터에서 직접 실험한 5단계입니다.

먼저 SA 토큰이 마운트됐는지 컨테이너 안에서 확인. 인증 없이 호출하면 401. 토큰을 붙여서 호출하면 401은 통과하지만 403 forbidden이 뜹니다 — RBAC 벽이죠.

Role과 RoleBinding을 적용하고 다시 호출. pods 조회 성공. 여기까지는 책과 같습니다.

마지막 단계가 핵심인데, **같은 토큰으로 services를 호출하면 여전히 403**입니다. Role에 pods만 있고 services는 없으니까요. 즉 권한이 정확히 부여된 리소스에만 적용된다는 거예요.

이게 왜 중요한가? 운영 자동화 도구에 권한 줄 때 "일단 다 풀어주자"는 유혹이 큽니다. 하지만 K8s는 정확히 필요한 것만 줄 수 있게 설계돼 있어요. **Least Privilege** 원칙을 자연스럽게 강제합니다.

**강조**: 권한은 정확히 그 자원에만 — 과허용 없음
**다음 슬라이드 연결**: "이번엔 실용적인 패턴 하나, Ambassador를 보겠습니다."

## 슬라이드 27: 책(2018) → 현재(2024+)

**예상 시간**: 2분

여섯 가지 변화입니다.

SA 토큰: 책 시점에는 Secret 기반 영구 토큰이었는데, 지금은 Projected Token입니다. 만료 시간이 있고 audit이 됩니다.

RBAC: 책에서는 "선택"이라고 표현하는데, 지금은 RBAC 안 켜져 있는 클러스터를 보면 이상한 거예요. 기본 활성입니다.

이미지: 두 개 다 노후됐어요. 실습할 때 교체 필수.

Downward API 필드: 듀얼스택 IP들이 추가됐고, hugepages도 노출 가능해졌어요.

In-place resize: 책 시점엔 없던 기능이고, v1.35에서 stable됐습니다. 이거 때문에 환경변수의 stale 문제가 더 중요해졌어요.

이런 차이를 알면, 책을 그대로 따라했다가 "왜 안 되지?"하는 함정을 피할 수 있습니다.

**강조**: 책 그대로 따라하면 안 되는 6가지

## 슬라이드 30: Q & A

**예상 시간**: 무제한

예상 질문 4개를 미리 보여드렸는데, 답을 미리 정리해두면:

**Q: env로 metadata.labels 받으려면?**
A: 전체는 안 됩니다, volume만. 단일 키(`metadata.labels['app']`)는 env로도 가능합니다.

**Q: limits 없는데 limits.cpu를 노출하면?**
A: 0이 아니라 node allocatable 최대값으로 채워집니다. 32GB 노드면 32GB가 들어와서 위험합니다. JVM Heap 자동 설정 같은 데서 문제될 수 있어요.

**Q: in-place resize 후 env / volume 동작 차이?**
A: volume은 자동 갱신, env는 컨테이너 재시작까지 stale. 그래서 리소스 의존 로직은 volume 권장.

**Q: Ambassador 패턴 vs 클라이언트 라이브러리?**
A: Ambassador는 언어 무관하고 가볍습니다. 라이브러리는 타입 안전, Informer 등 풍부한 기능. Operator 같은 본격 구현은 라이브러리, 가벼운 운영 스크립트는 Ambassador.

다음 챕터는 Deployments — Pod를 굴리는 법입니다. 감사합니다.
