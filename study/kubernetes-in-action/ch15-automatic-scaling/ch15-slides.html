HPA = 가로(개수), VPA = 세로(자원), CA = 노드. 이 세 단어면 구조가 잡힌다.

SCALE UP

수직 확장 — 기계를 더 키운다

✅ 장점

  • 단순함 — 코드 그대로
  • 분산 복잡성 없음
  • stateful·RDB에 적합

⚠️ 단점

  • 하드웨어 상한
  • SPOF
  • 보통 재부팅/다운타임
  • 고사양일수록 비용 폭증

예: DB를 4코어/16GB → 16코어/64GB로 교체 (RDS 인스턴스 클래스 업그레이드)

SCALE OUT

수평 확장 — 기계를 더 늘린다

✅ 장점

  • 거의 선형 확장
  • HA — 한 대 죽어도 OK
  • 범용 장비 (클라우드 친화)

⚠️ 단점

  • 앱이 무상태 전제
  • LB·데이터 일관성
  • 네트워크 → 복잡성↑

예: 웹 서버 1대 → 10대 + LB. DB는 read replica / 샤딩.

스케일링 안정화 — flapping 방지

spec:
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300  # 5분 보수
      policies: [{type: Percent, value: 50,

      stabilizationWindowSeconds: 0    # 즉시

CA

Cluster Autoscaler (CA)

⬆️ Scale up

Pod이 자원 부족으로 Pending(스케줄 실패) → 노드 그룹에 노드 추가.

⬇️ Scale down

활용률 낮고(기본 50%↓) Pod 재배치 가능 → drain 후 노드 제거.

HPA가 replica↑ → Pod이 Pending(노드 부족) → CA가 노드 추가 → Pod 스케줄됨

축소를 막는 요소(비용 누수 단골): 빡빡한 PodDisruptionBudget · local storage Pod · safe-to-evict:false · 시스템 Pod.

CA · 안전장치

PodDisruptionBudget (PDB)

"이 앱은 최소 몇 개는 항상 살아있어야 한다"를 선언 → CA/drain이 한꺼번에 너무 많은 Pod을 죽이지 못하게 막는 안전장치.

자발적 중단만 보호

✅ 보호 (voluntary)

  • kubectl drain
  • CA/Karpenter 노드 축소
  • 클러스터 업그레이드·롤링

❌ 못 막음

  • 노드 하드웨어 고장
  • 커널 패닉 · OOM kill
키의미
minAvailable축출 후에도 최소 N개 보장 (절대수 또는 50%)
maxUnavailable동시에 최대 N개까지만 죽임
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: {name: kubia}
spec:
  minAvailable: 3        # 또는 maxUnavailable: 1
  selector:
    matchLabels: {app: kubia}
# 책의 명령형 생성
kubectl create pdb kubia \
  --min-available=3 --selector=app=kubia
kubectl get pdb   # ALLOWED DISRUPTIONS 확인

⚠️ 함정: minAvailable = replica 수면 0개도 못 죽여 노드 축소가 영영 막힘(데드락) → 비용 누수. maxUnavailable: 1이 안전한 기본값.

왜 Karpenter가 더 빠른가 — 근본 2가지

① 프로비저닝 간접성

CA는 ASG desired만 +1 → 실제 기동은 ASG에 위임(루프 2개). Karpenter는 EC2 API 직접 호출.

② 노드그룹 = 고정 템플릿

CA는 그룹 중 고르기만 → 못 맞으면 재시도. Karpenter는 requests로 최적 타입 즉석 계산.

CA는 이식성(모든 클라우드) 위해 노드그룹 추상화를 거치느라 2단 루프+템플릿을 떠안음. 속도(이득) = 이식성 상실(비용), 같은 원인의 양면.

② 무엇을·어떻게 띄울지 선언

apiVersion: karpenter.sh/v1
kind: NodePool                 # 무엇을: 제약·한도
metadata: {name: default}
spec:
  template:
    spec:
      requirements:
      - {key: karpenter.sh/capacity-type, operator: In,
         values: ["spot","on-demand"]}
      nodeClassRef: {group: karpenter.k8s.aws,
        kind: EC2NodeClass, name: default}
  limits: {cpu: "1000"}              # 폭주 상한
  disruption: {consolidationPolicy: WhenEmptyOrUnderutilized}
---
apiVersion: karpenter.k8s.aws/v1
kind: EC2NodeClass             # 어떻게: AMI·서브넷·역할
metadata: {name: default}
spec:
  role: KarpenterNodeRole-$CLUSTER
  amiSelectorTerms: [{alias: al2023@latest}]
  subnetSelectorTerms: [{tags: {karpenter.sh/discovery: $CLUSTER}}]
  securityGroupSelectorTerms: [{tags: {karpenter.sh/discovery: $CLUSTER}}]
NodePool=어떤 노드를 허용할지(타입·spot·한도), EC2NodeClass=그 노드를 AWS에서 어떻게 만들지(AMI·서브넷·IAM). 노드그룹을 미리 안 만든다 — 제약만 주면 Karpenter가 즉석에서 고름.
DEMO · scale

Pod 늘리고 줄이기 → 노드가 따라온다

① 조작 (이게 트리거)

# 데모 워크로드 (pause, requests=1코어)
kubectl create deployment inflate \
  --image=registry.k8s.io/pause:3.9
kubectl set resources deploy/inflate --requests=cpu=1

# ▲ 늘리기 → Pending → Karpenter가 노드 생성
kubectl scale deploy/inflate --replicas=20

# ▼ 줄이기 → 빈/저활용 노드 자동 정리
kubectl scale deploy/inflate --replicas=0

② 관찰

kubectl get pods -w        # Pending→Running
kubectl get nodeclaims     # Karpenter 노드요청
kubectl get nodes -w       # 노드 증감
eks-node-viewer            # 비용·빈패킹 실시간
kubectl logs -f -n kube-system \
  -l app.kubernetes.io/name=karpenter

왜 requests가 필수? 스케줄러가 자리를 requests로 계산 → Pending 판정이 곧 Karpenter 입력. requests 없으면 못 늘림 (슬라이드 13 연결).

kubectl scale로 replica를 바꾸는 게 트리거. 실제 운영에선 이 replica를 HPA가 자동으로 올리고(부하↑), Karpenter가 노드를 받쳐줌 — HPA↔Karpenter 협력(다음 장 "세 층위 흐름").

KEDA — 이벤트 기반 + scale-to-zero

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
spec:
  scaleTargetRef: { name: consumer }
  minReplicaCount: 0   # ← 0까지
  maxReplicaCount: 50
  triggers:
  - type: kafka
    metadata:
      topic: orders
      lagThreshold: "100"

기본 HPA는 minReplicas:1 이하로 못 내려간다. KEDA는 이벤트 없으면 0으로 축소, 오면 깨워 이후 HPA에 위임.

Key Takeaways

  • HPA=가로(개수), VPA=세로(자원), CA=노드 — 세 단어로 구조가 잡힌다.
  • HPA 공식 ceil(replica × 현재/목표), CPU는 requests 대비 → requests 필수(ch14 직결).
  • HPA ↔ CA 협력, HPA ↔ VPA(동일 자원) 충돌 — VPA는 추천(Off) 모드로 병행.
  • metrics-server는 애드온 — 안 깔면 top·HPA 모두 <unknown>.
  • flapping은 behavior로, scale-to-zero는 KEDA로, 노드는 CA/Karpenter로.
