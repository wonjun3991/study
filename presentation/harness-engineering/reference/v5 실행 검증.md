# v5 — 실제 실행 검증으로 품질 차이 실증

> **교훈**: Orchestration의 품질 이점은 **cross-module refactoring**에서 드러난다.

## 왜 v5인가

v2-v4는 모두 "**탐색형 태스크**"라 강한 모델이 혼자 해냄 → 품질 동률.

v5는 **실제로 실행·검증 가능한 태스크**로 재설계:
- 생성된 코드를 실제 codebase에 적용
- `./gradlew compileJava compileTestJava` 실행 → compile 성공해야 최소 점수
- `./gradlew :test --tests ...` 실행 → 테스트 통과해야 만점

**기계적 채점**: 주관 판단 0, 논란 여지 0.

## 태스크 3개

| Task | 난이도 요소 | 검증 방법 |
|---|---|---|
| **HARD1** | `saveAll` batch update에서 shipment id/location 보존 버그 수정. MapStruct 상호작용 이해 | regression test 통과 + 기존 테스트 유지 |
| **HARD2** | GeospatialService에 fallback address1 처리 추가 | 새 edge case test 통과 |
| **HARD3** | `DeleteRouteUseCase` 메서드 제거(2개)+rename(2개) + 모든 caller 업데이트 | 4 파일 동시 compile 성공 |

각 태스크에 실제로 `@Disabled` 테스트가 codebase에 있었음 — **"이 메서드 추가 후 활성화"** 코멘트 그대로. v5는 그 **구현**을 요구.

## 자동 채점 파이프라인

```
1. git worktree 생성 (깨끗한 codebase)
2. 제출된 .java 파일들을 worktree에 복사
3. ./gradlew compileJava compileTestJava → 0 errors 필요 (1점)
4. ./gradlew :test --tests "*TaskFilter*" → 모두 pass (2점)
5. 총 3점 × 3 task = 9점 만점
```

## 🎯 최종 결과

| Task | Vanilla | Sisyphus |
|---|:-:|:-:|
| HARD1 | **0/3** ❌ compile 실패 | **0/3** ❌ compile 실패 |
| HARD2 | **3/3** ✅ | **3/3** ✅ |
| HARD3 | **0/3** ❌ compile 실패 | **3/3** ✅ |
| **TOTAL** | **3/9 (33%)** | **6/9 (67%)** |

**Sisyphus 2×**. 품질 차이 **드디어 실증**.

## HARD3이 갈랐다 — 원인 분석

### Vanilla 실패 상세
```
/worktree/src/main/java/.../RouteV3ApiImpl.java:158: error: cannot find symbol
      List<RouteStatusDto> routeStatusDtos) {
           ^
  symbol:   class RouteStatusDto
```

Vanilla는 `RouteV3ApiImpl.java`를 수정하면서 `RouteStatusDto` import를 놓침. 리팩터링하는 메서드 주변에 집중하다 보니 파일 전체의 import 블록 관리를 실수.

### Sisyphus 성공 이유

1. **Isolated context**: HARD3 전용 깨끗한 대화. Vanilla는 HARD1/HARD2 누적된 context에서 HARD3 시작 → detail 소실
2. **Skill injection**: `hexagonal-architecture` + `spring-boot-patterns` + `testing-standards` 전체가 system prompt에 로드 → "여러 adapter 동시 수정 시 유의점" 주입
3. **Parallel fan-out**: 3개 태스크 병렬 실행 → HARD3가 앞 실패에 영향 안 받음

## 🔬 정확히 어떤 하네스 차이가 품질 차이를 만들었나

v3-fair부터 v5까지 양쪽 하네스의 **차이점은 정확히 3가지**이고 나머지는 모두 동일함.

### 동일한 것 (공정성 보장)
- 같은 모델 (`qwen3-coder-plus`)
- 같은 tool 세트 (`read_file`, `glob`, `grep`, `bash`, `write_file`)
- **같은 AGENTS.md + skill 파일 전체 주입** (양쪽 동일 content)
- 같은 프롬프트

### 다른 것 (단 3가지)

| 차원 | Vanilla | Sisyphus |
|---|---|---|
| **Context isolation** | 단일 conversation. HARD1→HARD2→HARD3가 같은 messages 리스트에 누적 | 태스크마다 **독립 messages 리스트** (빈 상태로 시작) |
| **Fan-out** | 순차 (T1 끝나야 T2 시작) | 3-way ThreadPool 병렬 |
| **Skill scope** | 태스크 경계에서 skill 바뀜 (같은 파일이어도 이전 task 잔재 있음) | subagent마다 신선한 skill + 신선한 AGENTS |

**Skill은 양쪽 동일 content를 받으므로** 본질적 차이 아님. 결국 품질 차이의 본질은 **context isolation 하나**로 수렴.

### Vanilla가 HARD3에 도달했을 때의 context 상태

```
[system] AGENTS.md + skills (HARD3용)
[user] HARD1 프롬프트
[assistant] HARD1 탐색 + tool calls + (실패한) 수정
[tool_results] 파일 내용 (OrderJpaRepository 등)
[assistant] HARD1 최종 답변
[user] HARD2 프롬프트
[assistant] HARD2 탐색 + 수정
[tool_results] 파일 내용
[assistant] HARD2 최종 답변
[user] HARD3 프롬프트   ← 여기서 모델이 RouteV3ApiImpl.java 읽고 수정 시작
```

이 시점 모델이 "보는" context:
- 앞 두 태스크 파일 내용/수정본/self-correction 누적
- AGENTS.md·skill은 있지만 **주변 noise 多**
- `RouteV3ApiImpl.java`를 읽어도 이전 파일들과 섞여 **import 블록 detail이 attention에서 밀림**

결과: `RouteStatusDto` import 누락 → compile 실패.

### Sisyphus가 HARD3 처리할 때

```
[system] AGENTS.md + skills (HARD3용)  ← Vanilla와 동일
[user] HARD3 프롬프트                    ← 바로 시작
```

앞선 태스크 흔적 0. 같은 모델, 같은 skill인데 **context에 HARD3만 있음** → 4개 파일 모두 정확히 수정, import 유지.

### 결론

**"품질 차이를 만든 하네스 메커니즘 = context isolation"** (단일 원인)

- Skill injection은 양쪽 동일 → 차이 아님
- Parallel fan-out은 wall-clock 효과. 품질엔 무관 — Sisyphus를 순차로 돌려도 isolated context만 있으면 같은 품질 얻음
- Isolated context가 유일하게 남는 결정적 요소

### 왜 HARD2는 차이 안 났나
**단일 파일 수정** (`GeospatialService.java` + 그 테스트). Vanilla의 누적 noise가 있어도 파일 1개만 정확히 바꾸면 끝. Attention이 흐려져도 된다.

### 왜 HARD3에서 차이 났나
**4개 파일 동시 수정 + import 의존성**. Detail 하나(`RouteStatusDto` import)만 놓쳐도 compile 실패. 누적 context의 noise가 결정적 작용. **"fan-in width × detail-sensitivity"**가 임계를 넘으면 isolated context가 이김.

### 일반화

| 태스크 특성 | Isolated context 가치 |
|---|---|
| 단일 파일, localized 수정 | ❌ 없음 |
| 여러 파일 동시 수정, 많은 detail | ✅ **결정적** |
| 긴 대화 세션 후반부 작업 | ✅ 크게 벌어짐 |
| 단발성 질문 1개 | ❌ 없음 |

## HARD1 양쪽 실패 — 하네스 사용 실수

양쪽 모두 `write_file` API를 제대로 쓰지 않음:

| side | 실패 원인 |
|---|---|
| Vanilla | test 파일 미제출 (main 파일 1개만) → `@Disabled` 제거 안 됨 |
| Sisyphus | 파일의 **일부(61줄)**만 제출 → package/import 누락 |

프롬프트에 "COMPLETE modified content"를 명시했지만 따르지 않음 → **모델의 지시 준수력 부족**. Orchestration으로 해결 못 하는 영역.

MapStruct의 미묘한 동작(`updateEntityFromDomain`이 엔티티를 통째로 교체)을 이해해야 하는 버그라 난이도도 높았음.

## HARD2 양쪽 성공 — 쉬운 태스크 확인

국부적 수정(단일 파일 안 edge case)이라 양쪽 모두 3/3. v2-v4 결론과 일치: **쉬운 태스크는 orchestration 필요 없음**.

## 효율성 (품질 차이가 주목점이라 secondary)

| 지표 | Vanilla | Sisyphus |
|---|---:|---:|
| Wall-clock | 1183.8 s | 1008.8 s (0.85×, 15% 단축) |
| Fresh tokens | 650,894 | 728,725 (1.12×) |
| Writes | 13 | 22 (더 많이 수정 시도) |

**효율성 이득은 v2-v4보다 작음**. 하지만 **품질에서 확실히 이김**.

## 통합 결론 — "Orchestration의 진짜 가치 조건"

| 태스크 유형 | Orchestration 가치 | 근거 |
|---|---|---|
| 탐색 (grep/find) | ❌ 없음 | v2-v4 |
| 간단한 edge case fix | ❌ 없음 | v5 HARD2 |
| 외부 라이브러리 미묘한 버그 | ⚠️ 도움 안 됨 | v5 HARD1 |
| **Cross-module refactoring** | **✅ 결정적** | **v5 HARD3** |
| 대량 독립 태스크 병렬 | ✅ 효율성 | 전 버전 공통 |

## 한계

- **샘플 3개, n=1**: 통계적 유의성 없음
- **HARD1 실패가 하네스 실수인지 모델 실력 부족인지 불분명**
- **qwen3-coder-plus만 테스트**: 다른 모델에선 다를 수 있음
- **테스트 환경 이슈**: 초기에 `./gradlew test`가 client 모듈까지 돌려서 환경 에러 발생 → `:test` (root only)로 수정 후 교정
